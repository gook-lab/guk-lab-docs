# Notion 프로젝트 갤러리 패키지

프로젝트 여러 개를 Notion 데이터베이스와 상세 페이지로 옮길 때 사용합니다. 한
페이지를 다듬는 작업에는 필요한 절만 적용합니다.

## 사실 원장 — 작성 전 확인

각 프로젝트에서 다음 자료를 확인합니다.

- README·아키텍처·회고·결정 기록
- package manifest와 실제 소스 구조
- 테스트·측정 결과와 실행 명령
- Git 최초·최근 커밋, 배포 상태와 링크
- GitHub 저장소의 현재 이름과 공개 범위
- 사용할 이미지의 촬영 시점과 현재 화면 일치 여부

문서와 코드가 다르면 코드·Git·측정 기록을 기준으로 하고, 확인하지 못한 값은
`확인 필요`로 둡니다.

## 데이터베이스 속성

| 속성 | 형식 | 작성 기준 |
|---|---|---|
| Name | title | kebab-case 프로젝트 식별자 |
| Display Name | text | 화면에 보여줄 제품명 |
| Summary | text | 대상·기능·차별점 중 중요한 두 가지 |
| Period | text 또는 date | 실제 개발 기간 |
| Status | select | 운영·개발 중·중단·보관 |
| Role | text | 담당 범위와 기여 형태 |
| Stack | multi-select | 실제 사용한 주요 기술만 |
| GitHub | URL | 현재 저장소 주소 |
| Demo | URL | 현재 접속 가능한 경우만 |

`Name`과 `Display Name`을 분리합니다. 저장소는 `myeongri-seojae`처럼
kebab-case를 사용해도 본문 제목은 `명리서재`처럼 제품 표기를 유지할 수 있습니다.

기간을 추측해 연도만 채우지 않습니다. 커밋 이력으로 시작과 마지막 작업 시점을
확인할 수 있으면 그 근거를 사용하고, 중단한 프로젝트는 현재 개발 중으로 표시하지
않습니다.

## 상세 페이지 밀도

상세 페이지는 아래 질문에 답할 만큼만 작성합니다.

1. 누가 어떤 상황에서 사용하는 프로젝트입니까?
2. 직접 담당한 범위는 어디까지입니까?
3. 사용자가 얻는 주요 결과는 무엇입니까?
4. 구현 중 가장 판단이 필요했던 문제는 무엇입니까?
5. 실제 원인은 무엇으로 확인했습니까?
6. 어떤 선택을 했고 결과는 무엇으로 검증했습니까?
7. 현재 남은 제약과 다음 개선은 무엇입니까?

기능 수가 많아도 같은 사용자 흐름이면 한 절로 묶습니다. 문제 해결 사례는 개수를
맞추기 위해 늘리지 않고, 원인과 검증을 확인할 수 있는 사례만 사용합니다.

## 이미지 구성

프로젝트마다 다음 중 필요한 이미지만 선택합니다.

| 역할 | 권장 위치 | 내용 |
|---|---|---|
| cover | 페이지 커버 | 프로젝트를 한눈에 식별하는 대표 화면 |
| overview | 소개 다음 | 전체 화면이나 핵심 사용자 흐름 |
| feature | 주요 기능 | 기능별 대표 화면 |
| evidence | 문제 해결·검증 | 성능 결과, 테스트, 비교 화면, 다이어그램 |
| retrospective | 회고 | 이전 버전과 현재 버전, 남은 제약 |

같은 화면을 cover와 본문에 반복하지 않습니다. 이미지가 오래됐다면 현재 구현과 다른
부분을 캡션에 적거나 새로 촬영합니다. 로그인·이메일·개인 데이터·내부 URL은
가리거나 테스트 데이터로 교체합니다.

이미지 패키지를 만들 때는 다음 구조를 권장합니다.

```text
project-name/
├── README.md
├── cover.png
└── images/
    ├── 01-overview.png
    ├── 02-feature-name.png
    └── 03-evidence-name.png
```

본문의 이미지 위치에는 파일명과 캡션을 함께 적습니다. Notion에 가져온 뒤 파일을
어디에 넣을지 다시 판단하지 않게 하기 위한 표시입니다.

## 패키지 루트 색인

여러 프로젝트를 전달할 때 루트 README에 다음 정보를 표로 정리합니다.

- Notion Name
- Display Name
- 상세 README 경로
- cover 파일
- 본문 이미지 수
- GitHub·Demo 링크
- 확인이 필요한 항목

압축본과 압축을 푼 폴더를 함께 제공할 수 있습니다. 사용자가 바로 편집할 예정이면
압축을 푼 폴더를 기준본으로 두고, ZIP은 이동용 사본으로 취급합니다.

## 매체 간 대조

완료 전 다음 값을 README·Notion·이력서·웹에서 대조합니다.

- 프로젝트명과 저장소명
- GitHub·Demo URL
- 기간과 현재 상태
- 기술 스택
- 성과 수치와 측정 조건
- 주요 기능과 미완료 범위

문장 길이는 달라도 사실은 같아야 합니다. 저장소 이름을 바꿨다면 로컬 remote,
GitHub 링크, Notion 속성, 웹 포트폴리오와 패키지 색인을 함께 검색합니다.

## 완료 확인

- [ ] 기간·상태·역할을 실제 기록에서 확인했습니까?
- [ ] 문제 해결 사례마다 원인과 검증 방법이 있습니까?
- [ ] 회고에 남은 제약이나 다음 개선이 있습니까?
- [ ] cover와 본문 이미지가 현재 구현과 일치합니까?
- [ ] 이미지에 개인·회사 내부 정보가 남아 있지 않습니까?
- [ ] GitHub·Demo 링크가 현재 주소로 열립니까?
- [ ] 다른 포트폴리오 매체와 수치·기간·기술이 일치합니까?
