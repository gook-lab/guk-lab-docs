# 포트폴리오 워딩 정리

프로젝트의 사실은 유지하고, 읽는 사람이 판단 과정을 따라갈 수 있게 문장을
정리합니다. 문체와 헤딩은 저장소 루트의 `STYLE.md`를 따릅니다.

## 먼저 확인할 것

문장을 고치기 전에 가능한 범위에서 다음 원장을 확인합니다.

- README·아키텍처·결정 기록
- 실제 의존성 파일과 소스 구조
- 테스트 수·번들 크기·성능 측정 기록
- Git 기간·현재 상태·배포 링크
- 기존 이력서·Notion·웹 포트폴리오의 상충 문구

확인되지 않은 수치는 추정하지 않습니다. 문서끼리 충돌하면 더 큰 수치나 더 좋아
보이는 표현을 고르지 않고 코드·Git·측정 결과를 우선합니다. 확인할 수 없으면
`확인 필요`로 남깁니다.

## 공통 사실 카드

매체별 문장을 쓰기 전에 아래 사실을 한 번만 정리합니다.

- 프로젝트명과 저장소명
- 기간·상태·기여도·환경
- 대상 사용자와 해결하려는 문제
- 주요 기능
- 기술 선택과 책임 경계
- 문제·원인·해결·검증
- 정량 결과와 측정 조건
- 남은 제약과 다음 개선

이 카드가 README·Notion·이력서·웹 포트폴리오의 SSOT입니다.

## 서술 규칙

### 기능

기술명 목록이 아니라 사용자가 얻는 결과를 먼저 씁니다. 기술은 그 결과를 만든
방법을 설명할 때 붙입니다.

### 문제와 해결

가능하면 다음 네 요소를 보존합니다.

1. **문제와 영향** — 어떤 상황에서 무엇이 깨졌는지
2. **원인** — 측정·재현으로 확인한 실제 병목이나 제약
3. **선택** — 무엇을 바꿨고 왜 그 방법을 골랐는지
4. **검증** — 테스트·수치·회귀 게이트로 무엇을 확인했는지

원인이 확인되지 않았다면 해결한 것처럼 쓰지 않습니다. 상관관계를 원인으로
단정하지 않습니다.

### 회고

칭찬이나 성장 일반론보다 판단의 변화를 적습니다.

- 처음 가정과 실제 결과가 어떻게 달랐는지
- 범위를 줄이거나 설계를 바꾼 근거
- 아직 자동화하지 못한 검증과 이유
- 다시 한다면 먼저 측정하거나 분리할 지점

## 매체별 변환

### README

실행·아키텍처·검증을 재현할 수 있게 경로와 명령을 유지합니다. 구현 세부를 줄여
소개 문구만 만드는 작업이 아니라면 기존 기술 문서를 삭제하지 않습니다.

### Notion 프로젝트 상세

다음 흐름을 기본으로 사용하되 프로젝트에 맞게 줄이거나 합칩니다.

1. 기본 정보
2. 한 줄 소개
3. 프로젝트 소개
4. 진행 방식
5. 주요 기능
6. 이슈 해결
7. 검증 결과
8. 프로젝트 회고
9. 이미지 배치

문제 하나당 원인과 검증이 보일 만큼 설명하되 같은 사실을 여러 절에서 반복하지
않습니다.

### 이력서

지원 직무와 가까운 사례를 먼저 둡니다. 한 불릿에는 행동과 결과 하나를 담고,
기술 스택 전체를 경력 문장에 반복하지 않습니다. 개인 프로젝트는 대표 판단을
3~4개 불릿으로 압축합니다.

### 웹 포트폴리오

첫 화면은 정체성, 카드에는 대표 문제와 결과, 상세 페이지에는 근거를 둡니다.
문장을 억지로 한 줄에 맞추지 않고 의미 단위 줄바꿈을 사용합니다.

## 편집할 때 지울 것

- 근거 없는 "향상·강화·효율화·확장성"
- 주체와 대상이 없는 "구축·진행·적용"
- 같은 기술 스택의 반복
- 기능명만 이어지는 긴 문장
- 완료하지 않은 실험을 현재 성과처럼 보이는 문장
- 수치의 측정 조건을 없애 더 커 보이게 만든 표현
- `못박다·박아두다·잠그다·걷어내다`처럼 실제 동작을 대신하는 강조 동사
- `심장·주인공·썩는다`처럼 기술 대상을 의인화하는 상투적 은유

강조 동사는 문서와 코드에서 확인 가능한 동사로 바꿉니다.

- `기준을 못박았습니다` → `기준을 문서에 명시했습니다`
- `회귀 테스트로 박아뒀습니다` → `해당 사례를 회귀 테스트에 추가했습니다`
- `골든 데이터로 잠갔습니다` → `골든 데이터와의 차이를 검사합니다`
- `의존성을 걷어냈습니다` → `의존성을 제거했습니다` 또는 `경계를 분리했습니다`

`조용히`는 단순 강조로 쓰지 않습니다. 오류·경고가 발생하지 않는 것이 문제의 일부라면
무엇이 표시되지 않았고 사용자에게 어떤 상태가 남았는지 구체적으로 씁니다.

## 반복 문장 패턴 다듬기

다음 표현은 한 번 쓰면 자연스럽지만 여러 문단에서 반복되면 에이전트가 만든 문장처럼
보입니다.

- `A가 아니라 B입니다`는 실제 오해나 선택지를 바로잡을 때만 사용합니다. 단순 강조라면
  B를 직접 말합니다.
- `핵심은·문제는·중요한 건·결국`으로 문단을 연속해서 시작하지 않습니다. 결론 대신
  관찰한 사실이나 결정부터 씁니다.
- `반드시·절대·전부·유일한`은 코드·정책·측정으로 예외가 없음을 확인한 경우에만
  사용합니다. 그렇지 않으면 적용 조건과 범위를 밝힙니다.
- `경계·계약·게이트·불변식·SSOT·드리프트·파이프라인`은 필요한 기술 용어이므로
  금지하지 않습니다. 다만 한 문장에 겹쳐 쓰지 않고, 어떤 모듈·규칙·검사가 그 역할을
  하는지 함께 적습니다.
- `~것입니다`와 `~하도록 했습니다`가 이어지면 실제 행동을 서술하는 짧은 문장으로
  바꿉니다.

문단마다 표어처럼 굵은 결론을 만들지 않습니다. 강조 문장은 문단의 판단 하나에만
사용하고, 나머지는 근거와 결과가 읽히게 둡니다.

### 검색 신호

긴 문서를 교정할 때 아래 표현을 검색해 반복 횟수와 문맥을 확인합니다. 검색 결과를
일괄 치환하거나 단어 자체를 오류로 판정하지 않습니다.

```text
핵심은 | 중요한 건 | 문제는 | 결국
단순히 | 단순한 | 그냥 | 이게 | 이건
가 아니라 | 것입니다 | 할 수 있습니다 | 하도록 했습니다
구성했습니다 | 구축했습니다 | 진행했습니다 | 처리했습니다 | 관리합니다 | 보장합니다
일관되게 | 명시적으로 | 구조화 | 표면화
파이프라인 | 불변식 | SSOT | 경계 | 게이트 | 드리프트 | 폴백
무해하게 | 책임으로 | 책임 경계 | 실질적 난이도
유일한 | 전부 | 반드시 | 절대
```

검색 뒤에는 다음 기준으로 고칩니다.

- 지시어 `이게·이건`은 가리키는 대상이 앞 문장에 분명하지 않으면 대상 이름으로
  바꿉니다.
- `단순히·그냥`은 비교 대상을 낮추는 강조라면 지우고, 실제로 범위를 줄였다는 뜻이면
  줄인 조건을 적습니다.
- `구성·구축·진행·처리·관리`는 목적어와 변화가 모호할 때만 구체적인 동작으로
  바꿉니다.
- `보장합니다`는 테스트·타입·정책이 보장하는 범위를 함께 밝힙니다. 완전한 보장이
  아니면 `검사합니다`, `줄입니다`, `유지합니다`처럼 관찰 가능한 표현을 씁니다.
- `명시적으로·일관되게·구조화·표면화`는 무엇이 어디에 표현되거나 동일해졌는지
  설명하지 못하면 삭제합니다.
- `무해하게·실질적 난이도·책임으로`처럼 평가가 섞인 표현은 조건·영향·담당 범위로
  풀어 씁니다.

## 완료 전 확인

- 수치·기간·상태·기술이 실제 원장과 일치합니까?
- 첫 두 문단만 읽어도 무엇을 왜 만들었는지 알 수 있습니까?
- 각 해결 사례에 문제·원인·선택·검증 중 빠진 핵심이 있습니까?
- 기술명이 문장의 중심이 아니라 문제 해결의 수단으로 읽힙니까?
- 강조 동사와 은유를 `명시·추가·검사·제거·분리` 같은 실제 동작으로 바꿨습니까?
- 대조문·선언형 도입·절대어가 실제 의미 없이 반복되지 않습니까?
- 추상적인 기술 용어 옆에 구체적인 대상이나 검사 동작이 있습니까?
- 회고가 "배웠습니다"로만 끝나지 않습니까?
- 다른 매체와 표현은 달라도 사실은 동일합니까?
