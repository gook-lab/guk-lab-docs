# 운영 오류 재현 — 관측 로그에서 회귀 테스트까지

운영 오류를 알림으로 확인하는 데서 끝내지 않고, 재현 가능한 시나리오와 회귀
테스트로 바꾸는 흐름입니다. 자동 수정은 마지막 단계이며, 그 전에 같은 오류를
재현하고 수정 전후의 차이를 확인할 수 있어야 합니다.

## 목표 흐름

```text
Sentry 오류
  → Webhook 수신
  → Trace 정규화·중복 제거
  → GitHub Issue 생성·공유
  → 재현 시나리오 작성
  → 실패 테스트 확인
  → 수정
  → 동일 테스트 통과 확인
  → 회귀 테스트와 Docs 갱신
```

스케줄 리포트는 같은 자료를 기간별로 묶은 파생물입니다. 실시간 이슈와 주간
리포트가 서로 다른 기준으로 오류를 집계하지 않도록, 둘 다 정규화된 이벤트를
입력으로 사용합니다.

## 오류 이벤트 — 저장할 최소 정보

Webhook 원문 전체를 이슈에 붙이지 않습니다. 개인정보와 인증 값은 제거하고 재현에
필요한 필드만 남깁니다.

| 필드 | 용도 |
|---|---|
| 오류 유형·메시지 | 같은 오류의 중복 판별 |
| release·commit | 오류가 발생한 코드 식별 |
| 환경·브라우저·OS | 실행 조건 복원 |
| route | 최초 진입 경로 |
| trace·breadcrumb | 사용자 행동 순서 복원 |
| 요청 결과 | 읽기·쓰기·실패 지점 구분 |
| 최초·최근 발생 시각과 횟수 | 우선순위와 재발 여부 판단 |

이슈 fingerprint는 변하기 쉬운 줄 번호만 사용하지 않습니다. 오류 유형, 정규화된
스택 프레임, route와 release를 조합하고 동일 fingerprint의 이벤트는 기존 이슈에
발생 횟수와 최근 시각을 갱신합니다.

## 테스트 계층 — Vitest와 Playwright의 역할

### Vitest + Testing Library — 로직과 컴포넌트 상태

다음 항목은 브라우저 전체를 띄우기 전에 빠르게 확인합니다.

- 훅과 유틸의 입력·출력
- 로딩·성공·실패·빈 상태 분기
- 사용자 이벤트 뒤 컴포넌트 상태와 DOM 변화
- Query cache 무효화·refetch·rollback 순서
- 오류 경계와 재시도 UI

구현 내부의 함수 호출 수보다 사용자가 보는 결과와 외부 경계의 호출을 검사합니다.
Testing Library에서는 역할·레이블·텍스트로 요소를 찾고, 테스트 전용 id는 다른
선택 방법이 불안정할 때만 추가합니다.

### Playwright — 실제 사용자 경로와 시스템 연결

다음 항목은 브라우저에서 확인합니다.

- 로그인부터 오류 지점까지 이어지는 사용자 행동
- route 이동, 팝업, 새 창과 WebView 연결
- 실제 네트워크 요청의 경로·메서드·본문
- 읽기 성공 뒤 쓰기 실패, 오프라인, 세션 만료
- 브라우저별 렌더링과 상호작용 차이

Trace를 그대로 재생하는 것만으로는 부족합니다. 각 단계에 정상 조건을 붙이고,
오류가 발생했던 요청이나 화면 상태를 명시적으로 검사합니다.

## 재현 계약 — 실패부터 확인

에이전트가 수정에 착수하기 전에 아래 조건을 만족해야 합니다.

1. Trace의 동작을 사람이 읽을 수 있는 Given–When–Then 시나리오로 변환합니다.
2. 기존 코드에서 실패하는 테스트를 먼저 실행합니다.
3. 실패 메시지가 원래 오류와 같은 원인을 가리키는지 확인합니다.
4. 수정 뒤 같은 테스트가 통과하는지 확인합니다.
5. 테스트의 핵심 조건을 일부러 되돌려 다시 실패하는지 역검증합니다.

재현되지 않은 오류는 자동 수정 대상으로 넘기지 않습니다. 필요한 데이터나 실행
환경이 없으면 이슈에 `needs-reproduction` 상태와 부족한 조건을 기록합니다.

## WebGL 화면 — DOM 테스트와 시각 검증 분리

WebGL 뷰어는 헤드리스 브라우저의 GPU·코덱·드라이버 차이로 화면이 비거나 실제
제품과 다른 결과를 낼 수 있습니다. 이 상태에서 픽셀 스냅샷을 성공 기준으로 두면
제품 오류와 테스트 환경 오류를 구분하기 어렵습니다.

현재는 검증 범위를 다음처럼 나눕니다.

| 검증 대상 | 자동화 방식 |
|---|---|
| 도구 선택·버튼·패널·키보드 입력 | Playwright DOM·접근성 검사 |
| 좌표 변환·측정값·작도 제약 | Vitest 순수 함수·상태 테스트 |
| DICOM 로드·디코딩 상태 | 네트워크·상태 이벤트 검사 |
| WebGL 최종 픽셀 | GPU 실행 환경이 준비될 때까지 별도 시각 검증 |

GPU 환경이 준비되면 소프트웨어 렌더러와 실제 GPU 중 어느 쪽을 기준으로 삼는지,
허용 오차와 브라우저·장비 조합을 먼저 정합니다. 픽셀 비교를 추가하기 전에는 작은
고정 DICOM fixture와 결정적인 카메라·viewport 설정도 함께 준비합니다.

## GitHub Issue — 에이전트가 읽을 수 있는 입력

자동 생성 이슈에는 다음 순서를 유지합니다.

1. 사용자 영향과 발생 빈도
2. release·환경·route
3. 재현 단계와 단계별 정상 조건
4. 정규화한 trace와 관련 요청
5. 첨부 가능한 최소 fixture
6. 완료 조건

완료 조건에는 `오류가 사라짐` 대신 실행할 테스트와 확인할 결과를 적습니다. 예를
들어 `저장 요청 200 이후 목록에 새 값 표시`, `읽기 500에서 재시도 버튼 노출`처럼
관찰 가능한 상태를 사용합니다.

## 자동 수정 — 권한과 중단 조건

에이전트는 이슈 분석과 재현 테스트 작성을 먼저 수행합니다. 수정과 PR 생성은 별도
권한으로 다루며 다음 상황에서는 멈추고 사람에게 전달합니다.

- 개인정보가 제거되지 않은 이벤트
- 운영 데이터 없이는 재현할 수 있는 방법이 없는 경우
- WebGL 픽셀 결과만으로 성공 여부를 판단해야 하는 경우
- 재현 테스트가 원래 오류와 다른 이유로 실패하는 경우
- 데이터 삭제·권한 변경·외부 메시지 발송이 필요한 경우

PR에는 원본 이슈, 실패한 재현 테스트, 수정 후 결과와 남은 제약을 함께 남깁니다.

## 단계별 도입

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1 | Sentry Webhook → 이슈 초안 | 비밀정보 제거·중복 이슈 방지 |
| 2 | 스케줄 오류 리포트 | 동일 이벤트 원장에서 기간별 집계 |
| 3 | 자연어 시나리오 → 테스트 실행 | Docs의 검증 명령을 에이전트가 재현 |
| 4 | Trace → Playwright 초안 | 실패 테스트와 원본 오류의 원인 일치 |
| 5 | 수정 PR 제안 | 테스트 통과·역검증·사람의 리뷰 |
| 6 | WebGL 시각 검증 | GPU 기준 환경·fixture·허용 오차 확정 |

처음부터 자동 수정까지 연결하지 않습니다. 각 단계의 입력과 출력이 기록되고 사람이
같은 명령으로 재현할 수 있을 때 다음 단계로 넓힙니다.
