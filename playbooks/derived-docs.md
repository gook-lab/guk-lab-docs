# 손으로 고치는 표를 파생물로 — append-only 스트림과 재생성

여럿이 같은 레포에서 일할 때 제일 자주 깨지는 것은 코드가 아니라 **상태를 적어 둔
표**입니다. 현황판, 문서 목록, 체크리스트 — 각자 자기 행 하나를 고치는 파일이
가장 위험합니다.

`malt-index`(비공개 토이)에서 문서 허브를 `main` 직접 push 로 운영하며 겪은
것입니다. 원본 발상은 6명이 몇 달 돌린 실무 문서 레포에서 가져왔고, 두세 명
규모로 줄여서 배선했습니다.

## 증상 — 충돌이 아니라 조용한 유실

두 가지 방식으로 깨집니다.

| 상황 | 결과 |
|---|---|
| 같은 줄을 고침 | `git` 충돌. **시끄러워서 그나마 낫습니다** |
| 다른 줄을 고침 · 한 체크아웃 공유 | **last-write-wins. 아무 표시가 없습니다** |

두 번째가 진짜 문제입니다. 2026-08-25에 기능 에이전트 넷이 병렬로 돌면서
`docs/radio/README.md` 의 문서 목록 표를 각자 자기 행만 고쳤습니다. F3 의 저장이
**F2 의 행 갱신을 통째로 덮었습니다** — F2 문서는 21:10에 이미 만들어졌는데
표에는 21:14 시점에도 "미작성" 이 남아 있었습니다. 충돌 마커도, 경고도 없었습니다.

> 코드 레포에 워크트리 격리를 붙였어도 문서 레포는 체크아웃이 하나였습니다.
> **"격리했다" 가 어디까지인지 매번 확인해야 합니다.**

## 처방 — 상태의 원본을 표에서 스트림으로

표를 고치는 대신, **파일 끝에 줄만 덧붙이는 스트림**에 상태를 쌓고 표는 그것에서
만듭니다.

```
events/2026-08.jsonl        ← 여기에만 append. 기존 줄 수정·삭제 금지
       ↓ derive
status/BOARD.md 의 <!-- DERIVED:tasks --> 블록
```

한 줄이 완결된 JSON 객체입니다.

```json
{"ts":"2026-08-25T19:33:17+09:00","type":"task_state_change",
 "actor":"bottling","details":{"task":"t_0a552fb6","to":"done"}}
```

## append-only 는 왜 충돌하지 않나

`.gitattributes` 에 커스텀 머지 드라이버를 답니다. 하는 일은 **합집합 + 정확중복
제거 + 시각 정렬** 셋뿐입니다.

```
events/*.jsonl merge=jsonl-append
```

빈 레포로 재현해 봤습니다. 두 브랜치가 같은 파일 끝에 각각 한 줄씩 붙인 상태에서 —

| 드라이버 | `git merge` | 충돌 마커 |
|---|---|---|
| 미등록 | exit 1 | 1개 |
| 등록 | exit 0 | 0개 (세 줄이 시각 순으로 합쳐짐) |

⚠ **드라이버 정의는 `.git/config` 에 있어서 clone 을 따라오지 않습니다.**
등록 안 하면 git 이 `merge=jsonl-append` 를 **조용히 무시하고** 기본 3-way 로
돌아갑니다. 클론 직후 한 번 실행하는 스크립트를 두고, 문서에 그 사실을 적어
둡니다.

## 합집합이 되는 파일과 안 되는 파일

같은 방법을 아무 파일에나 쓰면 깨집니다. 판정 기준은 하나입니다 — **줄 하나가
혼자 서는가.**

| 파일 | 양쪽 다 남기기 | 왜 |
|---|---|---|
| `events/*.jsonl` | 됩니다 | 줄 = 완결 단위 |
| 배럴 파일 (`export` 줄 나열) | 됩니다 | 줄 = 완결 단위, 순서 무관 |
| `styles.css` | **안 됩니다** | 충돌 경계가 CSS 규칙 중간을 잘라 중괄호가 깨집니다 |

`styles.css` 는 `main` 을 기준으로 두고 브랜치에만 있는 선택자 블록을 **덩어리째**
뽑아 붙여 풀었습니다(한 브랜치 25블록 · 다른 브랜치 29블록). 줄 단위로 고르면
규칙이 반토막 납니다. 덩어리 파일이 자주 충돌하면 파일을 쪼개는 편이 낫습니다.

## 파생 말고 — 사람별로 쪼개기

공유 표를 없애는 방법이 파생만 있는 것은 아닙니다. **각자 자기 파일에 쓰게 하고
인덱스만 생성**하는 방법도 같은 문제를 풉니다.

```
docs/12-changelog/
├── _active-KYB.md   ← 이 사람만 편집
├── _active-JWS.md   ← 이 사람만 편집
│   … 기여자 7명
└── index.md         ← 병합 스크립트가 생성. 수동 편집 금지
```

```
docs/12-changelog/_active-*.md merge=union    # 같은 파일을 둘이 건드릴 일이 없음
docs/12-changelog/index.md     merge=ours     # 생성물이라 먼저 push 한 쪽 유지 후 재생성
```

둘 중 무엇을 고를지는 **내용을 누가 쓰느냐**로 갈립니다.

| | 파생 | 사람별 쪼개기 |
|---|---|---|
| 내용의 출처 | 기계가 판정할 수 있음(파일 존재, 상태 전이) | **사람이 서술해야 함**(무엇을 왜 했는지) |
| 예 | 문서 목록, 태스크 현황 | 변경 이력, 작업 노트 |
| 인덱스 | 원본에서 재생성 | 조각을 병합해 생성 |

파생은 사람이 쓴 문장을 담을 수 없고, 쪼개기는 조각이 늘어날수록 인덱스 생성이
필요해집니다. **한 파일에 여러 사람이 각자 자기 부분을 쓰고 있다면 둘 중 하나로
가야 한다**는 것이 공통점입니다.

## 손으로 적은 최댓값은 낡습니다

번호를 발급하는 문서에 *"현재 마지막 번호: 121"* 같은 줄을 두면 **반드시**
낡습니다. 갱신은 문서를 만든 사람의 몫인데 강제할 수단이 없기 때문입니다.

같은 레포에서 이 실패를 세 번 봤습니다.

| 어디 | 무슨 일 |
|---|---|
| 배포 문서 폴더 | 기록은 51, 실제는 61 (10건 지연) → 고친 뒤 다시 62 vs 66 (4건 지연) |
| 계획 문서 폴더 | 두 세션이 같은 날 101 을 동시 발급 |
| 트러블슈팅 인덱스 | 머리말 값이 두 달 전에서 멈춰, 그대로 따르면 **이미 있는 90여 개와 충돌** |

세 곳 모두 결국 같은 문장을 문서에 덧붙였습니다 — *"이 줄은 발급 근거가 아니라
사후 기록이다. 발급 전에 실측하라."* 그러느니 **처음부터 도구가 세게** 하는
편이 낫습니다.

```bash
python3 harness/unit.py next    # 스트림에서 max+1. 원격까지 fetch 후 계산
```

- 로컬만 보면 다른 머신이 발급한 번호를 못 봅니다. **발급 전 `git fetch` 하고
  원격의 스트림까지 합쳐서** 셉니다
- 그래도 완전히 못 막습니다(둘이 동시에 발급). 남는 중복은 **재생성 게이트가
  exit 1** 로 잡고, 표에 양쪽을 다 그려 누가 양보할지 사람이 정하게 합니다
- 별칭이 겹쳐도 데이터가 깨진 것은 아닙니다. 두 작업이 같은 이름을 쓴 것뿐입니다

## 파생 블록은 마커로 감쌉니다

문서 전체를 생성물로 만들면 사람이 쓴 산문을 둘 데가 없어집니다. **한 파일 안에
파생 블록과 산문을 같이 두고, 블록만 갈아끼웁니다.**

```markdown
<!-- DERIVED:tasks BEGIN -->
| 태스크 | 상태 |
...
<!-- DERIVED:tasks END -->
```

그러면 머지 속성을 걸 수 없습니다. `union` 은 표의 같은 행을 두 번 넣어 깨뜨리고,
`ours` 는 **상대가 쓴 산문을 소리 없이 지웁니다.** 둘 다 파생 블록 충돌보다
나쁩니다. 그래서 스트림에만 드라이버를 걸고, 파생 블록에서 충돌하면 **어느 쪽을
고를지 판단하지 않고 재생성**합니다.

```bash
git checkout --theirs status/BOARD.md   # 마커만 성하면 어느 쪽이든 됩니다
python3 harness/derive-board.py         # 합쳐진 events 에서 다시 만듭니다
```

## 파생은 결정론이어야 합니다

같은 입력이면 같은 출력이 나와야 합니다. 실행 시각을 찍으면 events 가 그대로여도
매번 결과가 달라져서 **커밋마다 잡음**이 생깁니다. "기준 시각" 이 필요하면
`datetime.now()` 대신 **이벤트의 최대 시각**을 씁니다.

## 무엇을 파생으로 옮길지

전부 옮기는 것이 아닙니다. 기준을 하나 두면 다음 사람이 같은 판정을 할 수
있습니다.

> **표에서 여러 사람이 각자 자기 행을 고치고 있으면 파생으로 옮길 때입니다.**

반대로 **도구가 판정할 수 없는 것은 옮기지 않습니다.** 완료 조건 체크리스트의
*"빈 상태 문구가 부정형이 아닌가"* 같은 항목은 사람이 눈으로 봐야 합니다.
그런 파일은 판정 가능한 항목만 빼고 나머지는 손으로 씁니다.

파일을 네 갈래로 나눠 두면 새 파일을 만들 때 어디에 속하는지 정할 수 있습니다.

| 갈래 | 규칙 | 충돌하면 |
|---|---|---|
| 스트림 | 줄 추가만 | 충돌하지 않습니다 |
| 파생 블록 | 손으로 고치지 않습니다 | 재생성합니다 |
| 산문 | 손으로 씁니다 | 사람이 읽고 풉니다. 진짜 충돌입니다 |
| 도구 | 평범한 코드 | 사람이 읽고 풉니다 |

## 커밋 전에 걸리게 합니다

파생물은 낡습니다. 최신인지 확인하는 명령을 두고, 어긋나면 **exit 1** 로
떨어뜨립니다. 화면에 표시만 하면 아무도 안 보고 흘러갑니다.

```bash
python3 harness/derive-board.py --check   # 어긋나면 exit 1
```

- 정상 동작은 조용하고 이상만 시끄러운 것이 게이트의 기본입니다. 매 실행마다
  정보성 로그가 아홉 줄씩 나오면 정작 볼 실패가 묻힙니다
- 게이트를 세웠으면 **깨뜨려 봅니다.** 일부러 어긋나게 만들어 exit 1 이 나오는지
  확인하고 나서 믿습니다 ([verification-gate](verification-gate.md))

## 정정은 새 줄로 합니다

기존 줄을 고치지 않는 것이 전제라, 잘못 들어간 이벤트는 `correction` 줄을 새로
넣어 덮습니다. 파생 때 대상 이벤트에 patch 를 얹습니다.

**되돌리기 장치로 쓰지 않습니다.** 나중에 사실이 바뀐 것(선행 링크가 나중에
걸린 것 등)은 정정이 아니라 **새 사건**입니다. 그때 기록이 비어 있던 것은
사실이고, `correction` 은 사실을 바꾸는 장치가 아니라 잘못 기록된 것을 고치는
장치입니다. 이 구분을 문서에 적어두지 않으면 다음 사람이 `correction` 을
"되돌리기" 로 씁니다.
