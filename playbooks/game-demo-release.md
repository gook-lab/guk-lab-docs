# 게임 공개 데모 마감 — 시작 · 실패 화면 · 소리 · 기록 수집 · 용량 · 휴대폰

[publishing](publishing.md)이 저장소를 공개하기 전의 확인 목록이라면, 이
문서는 배포 주소를 사람에게 돌리기 전의 확인 목록입니다. `moonhalo`(3D 무리
생존 게임, 2026-11-24)를 Vercel 에 올린 직후 "로딩 · 에러 · 404 는 처리돼
있나"라는 질문을 받았고, 셋 다 없었습니다. 같은 날 다섯 항목을 메우면서
항목마다 한 번씩 잘못 읽은 지점을 기록합니다.

## 점검 항목 — 배포 주소를 돌리기 전 다섯 가지

| 항목 | 없을 때 생기는 일 | 확인 방법 |
|---|---|---|
| 시작 화면 | 스크립트를 받는 동안 빈 화면 | 느린 회선을 흉내 내 1.5초 시점 촬영 |
| 실패 화면 | 멈춘 화면만 남고 다시 시작할 길이 없음 | 실패 상황을 강제로 만드는 스크립트 |
| 소리 풀기 | 타이틀 곡이 있어도 들리지 않음 | 재생 중인 곡 이름을 내는 확인용 값 |
| 판 기록 수집 | 사람 플레이 수치가 한 건도 없음 | 공개 키로 읽기 · 지우기가 거부되는지 호출 |
| 용량 · 휴대폰 | 첫 방문 수십 MB, 가로 화면에서 버튼이 화면 밖 | 전송량 계측, 세로 · 가로 두 크기 촬영 |

## 시작 화면 — 스크립트보다 먼저 보이는 로딩 틀

- 로딩 화면은 `index.html` 에 인라인 CSS 와 함께 둡니다. 번들이 받아지기
  전에 보여야 하므로 스크립트로 만들지 않습니다.
- 진행 막대는 실제 단계(설정 파일 → 타이틀 그림)에 묶고, 그림 미리 받기에는
  시간 상한(8초)을 둡니다. 느린 회선에서 로딩이 끝나지 않는 일을 막습니다.
- 무거운 3D 모델은 로딩을 막지 않습니다. 절차 메시로 먼저 그리고, 타이틀
  구석에 "모델을 받는 중이에요 n / 9"만 띄웁니다. 화면 가운데에 늘 보이는
  주인공 모델을 가장 먼저 받습니다.

## 실패 화면 — 시점별 다섯 경로

실패는 일어나는 시점마다 잡는 자리가 다릅니다.

| 시점 | 원인 | 잡는 자리 |
|---|---|---|
| 스크립트 받기 · 평가 | 오프라인, 배포 직후의 옛 주소 | `index.html` 인라인 스크립트의 `error` 리스너(캡처 단계) |
| 렌더러 생성 전 | WebGL2 를 켤 수 없는 기기 | 임시 캔버스의 `getContext('webgl2')` 확인 |
| 판 도중 | 게임 루프 예외 | 프레임 함수의 `try/catch` → 안내 후 루프 정지 |
| 판 도중 | 그래픽 장치 끊김 | `webglcontextlost` 에서 일시정지 · 안내, 복구되면 안내 제거 |
| 주소 오류 | 없는 경로 | `public/404.html` (정적 호스팅이 404 응답에 사용) |

- 시작 전 오류 리스너는 모듈보다 먼저 등록돼야 하므로 인라인으로 둡니다.
  그림 한 장의 실패까지 치명으로 잡지 않도록 `SCRIPT` 요소와 예외 객체가
  있는 경우로 좁힙니다.
- 시작 뒤에는 게임 루프의 예외만 치명으로 봅니다. `window` 의 `error` 전체를
  치명으로 잡으면 버튼 하나의 오류가 판 전체를 덮습니다.
- 개발 서버는 없는 경로에 `index.html` 을 돌려주므로 404 는 배포 주소에서
  상태 코드로 확인합니다.
- 다섯 경로를 한 번에 만드는 확인 스크립트를 둡니다. 요청 차단으로 스크립트
  실패를, `getContext` 덮어쓰기로 WebGL 불가를, `WEBGL_lose_context` 로 장치
  끊김을, 시뮬레이션 함수 바꿔치기로 루프 예외를 만듭니다.

## 소리 — 첫 입력 전 재생 차단과 들어가기 단계

타이틀 곡 파일이 있었는데도 타이틀에서 들리지 않았습니다. 브라우저는 첫
입력 전에 재생을 막는데, 타이틀은 화면 아무 곳이나 누르면 판이 시작되는
구조라 첫 입력과 동시에 전투 곡으로 넘어갔습니다.

- 로딩이 끝나면 "눌러서 들어가요" 단계를 하나 둡니다. 이 입력으로 소리가
  풀리고, 타이틀은 그 뒤에 그립니다.
- 들어가기 단계의 키 입력은 캡처 단계에서 멈춥니다. 멈추지 않으면 같은 키가
  뒤에 있는 게임 단축키로도 전달됩니다.
- 재생 여부는 확인용 값(곡 이름 · `AudioContext` 상태)으로 자동 확인합니다.
  음량과 분위기는 사람이 들어야 합니다.
- 화면 촬영 도구는 들어가기 단계를 넘기도록 고칩니다. 고치지 않으면 이후
  촬영이 전부 그 화면으로 찍힙니다.

## 판 기록 수집 — 쓰기 전용 테이블 · 익명 · 자동화 제외

목적은 [밸런스 하네스](balance-harness.md)의 합격선을 사람 수치로 보정하는
것입니다. 클라우드 저장은 로그인이 필요하고 순위표는 브라우저 계산이라 조작을
막기 어려워, 판 결과 한 줄을 모으는 것부터 붙였습니다.

- **전송**: 판이 끝날 때와 판 도중에 창을 닫을 때 `fetch` 로 한 줄을
  보냅니다. `keepalive` 를 켜고 실패는 무시합니다. 의존성은 추가하지 않습니다.
- **권한**: 행 수준 보안을 켜고 공개 키에는 쓰기만 엽니다. 열마다 범위와
  크기 제약을 둡니다. 공개 키로 읽기(401) · 지우기(401) · 범위 밖 값 쓰기
  (400)를 실제로 호출해 확인합니다.
- **비밀 값**: 빌드 산출물에 서비스 키 · DB 비밀번호가 들어갔는지 값으로
  대조합니다. 이름으로 찾으면 토큰 안에 인코딩된 글자를 놓칩니다.
  `import.meta.env` 를 객체째 읽으면 `VITE_` 변수 전부가 번들에 들어가므로
  이름을 하나씩 짚어 읽습니다.
- **섞이지 않게**: 수집 주소가 없는 빌드(로컬 · 하네스)는 아무것도 보내지
  않습니다. 봇과 자동화 브라우저(`navigator.webdriver`)도 제외하고, 확인할
  때만 쿼리로 엽니다. 확인이 끝나면 시험 기록을 지웁니다.
- **사용자 선택**: 설정 화면에 끄기 스위치와 수집 항목 안내를 둡니다.
- **버전 구분**: 배포할 때 빌드 표시(커밋 해시)를 환경 변수로 넣어 한 열에
  남깁니다.
- **요약 도구**: 하네스 합격선과 같은 지표 이름으로 나란히 출력하고, 20건
  아래에서는 경고를 붙입니다.

잘못 읽은 지점이 둘 있었습니다. 촬영 도구가 판이 끝나고 1.5초 뒤에
브라우저를 닫아 첫 전송이 나가지 않았습니다(2.5초 이상으로 늘림). 제약에
걸려 실패한 쓰기도 일련번호를 하나 쓰므로, 번호가 건너뛴 것만 보고 기록이
유실됐다고 판단하면 안 됩니다.

## 용량 — 표시 크기에 맞춘 텍스처와 캐시 설정

- **먼저 내용을 봅니다.** Meshy 가 준 GLB 2.4 MB 중 2048² 기본색 텍스처가
  2.2 MB, 지오메트리는 0.2 MB 였습니다. 텍스처 한 장의 GPU 메모리는 22 MB
  로, 모델 15개면 330 MB 입니다.
- **표시 크기에 맞춥니다.** 화면에서 50px 안팎인 괴물 · 지형지물은 512,
  크게 보이는 주인공 · 보스는 1024 로 줄이고 WebP 로 바꿨습니다. 모델과
  그림 합계 **49.0 MB → 4.7 MB**, 전후 화면 비교에서 차이는 보이지
  않았습니다.
- **지오메트리 압축은 뺐습니다.** 로더가 정점 속성을 직접 변환하는 구조에서는
  양자화된 속성이 범위를 벗어나 깨질 수 있고, 줄일 수 있는 양도 작았습니다.
- **캐시 설정을 확인합니다.** 개발 중 새 파일을 바로 보려고 넣은
  `cache: 'no-store'` 가 남아 있어, 방문할 때마다 모델 45 MB 를 새로 받고
  있었습니다. `no-cache`(바뀌었는지만 묻기)로 바꿨습니다.
- **파일 크기가 아니라 전송량을 잽니다.** 브라우저의 네트워크 계측으로 첫
  방문 6.6 MB, 재방문 0 MB 를 확인했습니다.

측정 구간을 2.5초로 잡았을 때는 재방문에 소리 3 MB 가 잡혀 캐시가 안 되는
것으로 읽을 뻔했습니다. 소리 파일은 들어간 뒤에 받기 시작해 첫 방문 구간
안에 끝나지 않았던 것이고, 9초로 늘리니 재방문은 0 이었습니다. 배포 직후의
첫 요청은 옛 버전이 오는 경우도 있어, 결과가 이상하면 한 번 더 돌립니다.

처리 스크립트는 이미 처리한 파일을 건너뛰게 만들어 저장소에 둡니다. 모델을
새로 만들 때마다 다시 돌리는 단계가 됩니다. 이미지 전환 규칙은
[web-optimization](web-optimization.md)을 따릅니다.

## 휴대폰 화면 — 세로 · 가로 두 크기와 낮은 높이 보정

- 세로(390×844)와 가로(844×390)로 전 화면을 찍어 묶음으로 봅니다. 터치
  입력과 `pointer: coarse` 를 켠 상태로 엽니다.
- 깨진 곳은 가로뿐이었습니다. 모달 높이를 화면의 90% 로 고정해 둔 탓에
  높이 390 에서는 351px 만 남아, 결과 화면의 "다시 하기" 버튼이 스크롤 밖으로
  밀리고 목록은 한 줄도 온전히 보이지 않았습니다.
- 폭이 아니라 높이 기준 미디어 쿼리(`max-height: 520px`)로 여백을 줄이고
  버튼을 아래에 고정했습니다. 폭 기준 쿼리만 있으면 가로 화면은 데스크톱
  배치를 그대로 받습니다.
- 터치 이벤트를 직접 보내 끌어서 이동 · 손 떼면 멈춤을 확인하고, 조작 안내
  문구를 터치용으로 가릅니다.

## 남는 한계 — 사람과 실제 기기로만 확인되는 것

위 확인은 전부 터치를 흉내 낸 데스크톱 크롬 결과입니다. 실제 휴대폰의 프레임
속도, 사파리의 소리 정책과 창 닫기 전송, 음량과 손맛은 확인하지 못했습니다.
기록 수집에 fps 와 입력 방식을 같이 남겨 이 빈칸을 사람 플레이로 메우도록
했습니다.
