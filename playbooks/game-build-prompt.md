# 게임 제작 프롬프트 틀 — 우선순위 · 숫자 목표 · 화면만 보는 비평가 · 끝 조건

에이전트에게 게임을 맡길 때 쓰는 프롬프트 틀입니다. 잘 나온 공개 사례들은 먼저 설계하고, 참고 자료를 주고, 결과를 스스로 보고 고치게 했습니다. 우리 게임 프롬프트(rift-dungeon · dokkaebi-quest · water-balloon-arcade · spire-godot)를 2026-11-24에 그 기준으로 대조했습니다. 설계와 참고 자료는 넘칠 만큼 있었고, **우선순위 · 끝 조건 · 만든 쪽과 분리된 비평가**가 비어 있었습니다.

## 빈칸이 만든 문제 — 자기 채점과 시각으로 끝나는 루프

- dokkaebi-quest 는 자체 진단 점수(GUIHON_PARITY)를 99%까지 올렸지만, 2026-10-28 에 "점수는 완성도가 아니다"로 판단을 바꿨습니다. 점수를 매긴 쪽과 만든 쪽이 같았습니다.
- rift-dungeon 은 봇 시험이 448개까지 통과했지만 "사람 손 손맛 확인"이 마일스톤 2부터 계속 남은 일이었습니다.
- 야간 루프는 07:00 같은 시각으로 끝났습니다. 관문을 통과해서 끝난 것이 아니었습니다.

## 틀 — 여덟 칸

프롬프트나 `PLAN.md` 머리에 아래 여덟 칸을 둡니다. 비어 있는 칸은 "없음"이라고 적습니다.

| 칸 | 적는 것 | 예 |
| --- | --- | --- |
| 목표 | 한두 문장. 무엇이 되면 되는지 | 방 하나에서 콤보 · 띄우기 손맛을 평가할 수 있다 |
| 참고 | 그림 · 영상 · 기준표 경로. 이름만 던지지 않습니다 | `docs/feel-spec.md`, 사용자가 준 스크린샷 |
| 우선순위 | 충돌할 때 지킬 순서. 셋 이하 | 1 손맛 2 읽힘 3 프레임 안정 |
| 제약 | 쓰지 않을 것 · 써야 할 것 | 외부 그림 파일 없음, 특정 게임 이름 · 그림 금지 |
| 숫자 목표 | 기계로 잴 수 있는 값과 잰 방법 | 한 판 동안 33ms 넘는 프레임 0회(측정 스크립트) |
| 검증 | 누가 무엇을 보고 통과를 판정하는지 | 아래 「화면만 보는 비평가」 |
| 끝 조건 | 검증 관문 이름과 통과 조건 | 비평가의 치명 · 큼 0개, `pnpm verify` 통과 |
| 물어볼 일 | 되돌릴 수 없는 일 · 돈이 드는 일 | push · 배포 · 공개 · 유료 API |

## 화면만 보는 비평가 — 코드를 모르는 새 서브에이전트

- 라운드마다 **새** 서브에이전트를 띄웁니다. 앞 라운드 대화를 이어 쓰지 않습니다.
- 비평가에게는 렌더 스크린샷 · 프레임 묶음 그림 · 짧은 영상과 "이 장면이 무엇을 보여 줘야 하는지" 한 줄만 줍니다. 코드 · diff · 만든 쪽의 설명은 주지 않습니다.
- 비평가는 고칠 점을 심각도(치명 · 큼 · 보통 · 사소함)와 함께 **다섯 개까지** 냅니다. 각 항목에 그림의 어느 부분인지 적게 합니다.
- 만든 쪽은 치명 · 큼부터 고치고 같은 장면을 다시 찍습니다. **치명 · 큼이 0개면 그 장면은 통과**입니다. 새 비평가는 라운드마다 새 보통 · 사소함 지적을 내므로, 보통 이하는 기록만 합니다.
- 만든 쪽이 정할 수 없는 지적(색 토큰 · 디자인 사양 · 범위 같은 사용자 결정)은 관문에서 빼고 "사용자 결정 대기"로 넘깁니다.
- 라운드는 다섯 번까지입니다. 넘으면 남은 지적과 함께 "진행 중"으로 적고 멈춥니다.
- 같은 지적이 두 라운드 연속 나오면 고치는 방향이 틀린 것입니다. 숫자를 조정하기 전에 원인을 다시 봅니다.

## 진짜와 구별되나 — 참고 화면을 섞은 블라인드 고르기

참고 화면이 있을 때만 씁니다. 비평가에게 참고 화면과 우리 렌더를 섞어 보여 주고, 어느 쪽이 완성된 게임인지 고르게 합니다. 들켰다면 들킨 이유를 다음 라운드의 고칠 점으로 씁니다.

- 참고 화면은 **채점에만** 씁니다. 캐릭터 · 그림 · 맵 · UI 배치를 베끼는 근거로 쓰지 않습니다. 특정 게임을 다시 만드는 작업이 되면 멈춥니다.
- 질문은 "좋아 보이나"가 아니라 "완성품과 같은 수준으로 보이나"입니다.

## 숫자 목표 — 잰 방법까지 한 줄에

- 숫자 하나에 잰 방법 하나를 붙입니다. 잴 도구가 없으면 첫 작업 묶음에서 도구부터 만듭니다.
- 손맛 같은 감각 값은 기준표(예: rift `feel-spec.md`)의 숫자로 적고, 통과는 비평가와 사람 손이 판정합니다.
- 봇 시험은 회귀 관문입니다. 봇이 깨는 것과 사람이 재미있는 것은 다른 관문입니다.

## 사람 승인 지점 — 되돌릴 수 없는 일만

push · 배포 · 공개 · 유료 API 호출 · 데이터 삭제는 사람에게 묻습니다. 읽기 · 로컬 실행 · 스크린샷 · 시험은 묻지 않습니다. 레포마다 이미 정한 승인 규칙이 있으면 그것을 따릅니다.

## 운영에서 고친 점 — 통과 기준과 출구 (2026-11-24)

rift-dungeon 첫 적용에서 비평가 관문을 6라운드 돌렸습니다. 넘침 · 글자 뭉개짐은 고쳤지만, "등급 색이 서로 가깝다"는 지적이 네 라운드 연속 나왔습니다. 원인은 만든 쪽이 정할 수 없는 디자인 토큰이었습니다. 또 새 비평가는 라운드마다 새 지적을 내서 "사소함만 남음"에 닿기 어려웠습니다. 그래서 통과 기준을 치명 · 큼 0개로 바꾸고, 사용자 결정 출구와 라운드 상한을 넣었습니다.
