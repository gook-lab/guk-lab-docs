# 화면이 말해주지 않는 것 — 읽기와 쓰기

화면을 열어 보고 "됐다" 고 판단하는 것은 절반만 보는 것입니다. 한 프로젝트에서
**같은 모양의 결함이 하루에 세 번** 났는데, 셋 다 화면은 멀쩡했고 테스트도
CI 도 통과했습니다.

## 세 번 다 같은 자리였습니다

| 무엇 | 그릴 때 | 보낼 때 |
|---|---|---|
| `fetch` 가 `this` 를 잃어 요청이 안 나감 | GET 은 목이 받아 정상 | POST 만 진짜 `fetch` 로 가 브라우저가 거부 |
| 낙관 반영 되돌림 | 누르는 즉시 그려짐 | 되돌림은 응답이 와야 돎 — 목엔 실패가 없어 한 번도 안 돌음 |
| 시트가 빈 라우트 파라미터를 들고 뜸 | 목록에서 이미 받은 값으로 그려짐 | 빈 id 가 **쓰기 요청에서만** 쓰임 |

증상은 셋 다 *"눈으로 보면 정상인데 눌러야 드러난다"* 였습니다. 원인은 하나로
좁혀집니다 — **그리는 데 쓰는 값과 보내는 데 쓰는 값이 달랐고, 화면은 앞의
것만 보여 줍니다.**

> **읽기는 되는데 쓰기가 안 되는 자리는 화면으로 판단할 수 없습니다.**

첫 번째는 특히 고약했습니다. 오류가 `catch` 에서 뭉개져 화면에는 *"잠시 후 다시
시도해 주세요"* 만 떴고, **서버 로그에는 아무것도 안 찍히는데 네트워크 탓처럼
읽혔습니다.**

## 그래서 이렇게 합니다

**확인할 때 한 번 눌러 봅니다.** 뜨는 것을 보는 것으로는 절반입니다. 목록을
열었으면 항목을 하나 고치거나 지워 보고, 폼을 열었으면 제출해 봅니다.

**요청이 실제로 나가는지는 받아 적습니다.** 화면은 오류를 삼킬 수 있고, 삼키면
"안 나간 것"과 "나갔는데 실패한 것"이 같아 보입니다. 요청을 받아 적는 작은
서버를 띄우고 무엇이 도착했는지 셉니다.

```
GET  /api/me · /api/meets · /api/search
POST /api/meets/m1/attend · /api/sightings
```

도착한 목록이 곧 증거입니다. 0건이면 배선이 안 된 것이고, 그건 화면으로는
구분되지 않습니다.

## 주입한 의존은 기본 경로를 안 밟습니다

테스트에서 `fetch` 를 갈아끼우면 경로·메서드·본문은 정확히 검사할 수 있지만
**진짜 `fetch` 로 도는 경로를 한 번도 안 밟습니다.** 주입한 것은 평범한 함수라
`this` 문제가 없습니다. 위 첫 번째 결함이 그 틈으로 지나갔습니다.

주입 테스트를 버리라는 뜻이 아닙니다. **둘이 잡는 것이 다릅니다.**

| 방식 | 잡는 것 |
|---|---|
| 주입 의존 | 경로 · 메서드 · 본문 · 호출 여부 |
| 기본 경로 | 그 의존이 실제 환경에서 부를 수 있는가 |
| 화면에서 누르기 | 누르는 자리가 정말 그 함수를 부르는가 |

셋 다 필요합니다. 앞의 둘은 자동화되고, 마지막은 사람이 합니다.

## 실패를 만들어야 실패 처리가 돌아 봅니다

목은 실패하지 않습니다. 그래서 **오류·되돌림·재시도 코드는 서버가 붙는 날
처음 돕니다.** 그날 처음 도는 코드는 대개 틀려 있습니다.

받아 적는 서버에 모드를 붙이면 그 경로를 미리 밟을 수 있습니다.

| 모드 | 무엇을 밟나 |
|---|---|
| 쓰기에만 실패 | 낙관 반영 되돌림 · 토스트 · 재시도 |
| 읽기에만 실패 | 오류 상태 화면 · 인라인 재시도 |
| 세션만 성공 | 로그인 가드를 지나 안쪽 화면까지 |

읽기에만 실패시키자 **서버 오류를 "아직 아무것도 안 했다" 로 그리던 화면**이
나왔습니다. 이용자는 자기 탓인 줄 알고 다시 시도할 길도 없었습니다. 온보딩
분기가 목록 자리를 *대신하고* 있었기 때문인데, 덧붙는 것과 대신하는 것은
다릅니다.

그런 분기는 **처음 오는 사람 자리에 몰립니다** — 온보딩·튜토리얼·빈 상태.
하필 그 자리가 서버 상태를 가장 오해하기 쉬운 자리입니다.

## 오프라인은 실패가 아닙니다

연결이 끊긴 것과 서버가 500 을 준 것은 다릅니다. 앞은 저장해 둔 것을 보여주고
재시도를 **띄우지 않아야** 하고, 뒤는 재시도를 띄워야 합니다. 한 삼항연산자에
섞어 쓰면 오프라인에 재시도 버튼이 붙습니다.

서버에 500 을 시키는 것으로는 오프라인을 만들 수 없습니다. 웹이라면 화면 쪽에서
`navigator.onLine` 과 `online`/`offline` 이벤트를 바꿉니다.

```js
Object.defineProperty(navigator, 'onLine', { get: () => false, configurable: true })
window.dispatchEvent(new Event('offline'))
```

같은 상태에 문구가 갈리기도 쉽습니다 — 한 프로젝트에서 오프라인 문구가
**21곳 9가지**였고 어휘가 두 벌이었습니다. 탭을 옮길 때마다 같은 일에 다른 말을
듣습니다.

## 요약

1. **뜨는 것을 보는 것으로는 절반입니다.** 확인할 때 한 번 눌러 봅니다
2. 요청이 나가는지는 **받아 적어** 셉니다. 0건은 화면으로 구분되지 않습니다
3. 주입 의존 테스트는 **기본 경로를 안 밟습니다.** 둘 다 둡니다
4. **실패를 만들어야** 실패 처리가 돌아 봅니다 — 쓰기·읽기·세션을 따로 실패시킵니다
5. **오프라인은 실패가 아닙니다.** 재시도를 띄우는지로 갈립니다
