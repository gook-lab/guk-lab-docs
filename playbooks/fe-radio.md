# 방법론을 RADIO로 정리하면

토이 프로젝트들에서 자리 잡은 방법론을 **FE RADIO 전략**(GreatFrontEnd의
RADIO Framework에 C/V 게이트를 붙인 확장판)의 틀로 다시 정리한 문서예요.
플레이북과 결정 기록이 프로젝트별로 흩어져 있는데, 설계 순서라는 축으로
꿰어 보면 "다음 프로젝트에서 어느 단계에 뭘 챙길지"가 한눈에 보이거든요.

```
Gate In ─ C  Context        기존 코드·패턴·컨벤션 파악

          R  Requirements   문제 정의 + 기능/비기능 + 스코프 아웃
 RADIO    A  Architecture   주요 컴포넌트 + 책임 할당
          D  Data Model     엔티티, 필드, 데이터 출처/생명주기
          I  Interface      경계를 넘는 계약 (API, props, 이벤트)
          O  Optimizations  NFR에서 도출된 항목만 (YAGNI)

Gate Out ─ V  Verification  완료를 증명하는 검증
```

> 라디오를 켜기 전에 **주파수를 맞추고**(C), 끝나면 **수신을 확인한다**(V).

여기 있는 내용은 새로 만든 규칙이 아니라, 이미 각 프로젝트에서 값을 치르고
얻은 것들을 단계별로 다시 배치한 거예요. 원문은 각 링크로 가리키고
복사하지 않아요.

## 한눈에 보기

| 단계 | 핵심 질문 | 토이에서의 실천 |
|---|---|---|
| **C** Context | 이미 만들어 둔 게 있나? | [하네스 카탈로그](../harness/README.md)부터 확인 |
| **R** Requirements | 무엇을 하고, 무엇을 안 하나? | 스코프 아웃을 문서에 명시 — "오늘의 운세는 안 한다" |
| **A** Architecture | 조각과 책임은? | 시뮬/렌더 분리, SSOT에서 파생 |
| **D** Data Model | 데이터는 어디서 오고 어디 사나? | 콘텐츠는 순수 데이터, 좌표계는 타입으로 분리 |
| **I** Interface | 경계에서 무엇이 오가나? | 외부 데이터는 문 앞에서 검증, 외부 API 앞에 게이트 하나 |
| **O** Optimizations | NFR에서 나온 최적화만 | [measure-first](measure-first.md) — 재고 나서 고쳐요 |
| **V** Verification | 완료를 어떻게 증명하나? | [verification-gate](verification-gate.md) · 헤드리스 하네스 · 외부 권위 대조 |

## C — Context: 이미 만들어 둔 게 있나

새 프로젝트를 시작할 때 [하네스 카탈로그](../harness/README.md)를 먼저
봐요. 프로젝트별 `.claude/` rules·skills·commands 전수 목록이라,
"이런 걸 이미 만들어 뒀나?"에 바로 답해줘요. 실제로 서로 모르는
프로젝트들이 같은 네 가지 문제(scaffold-* / validate-* / 하네스 동기화 /
verify-*)를 각자 풀어놨더라고요 — C를 건너뛰면 다섯 번째로 또 풀게 돼요.

React·TS 프로젝트라면 `pig/.claude/rules/`(18개)부터 복사해서 깎는 게
빨라요.

## R — Requirements: 스코프 아웃을 적어둬요

"무엇을 하지 않는가"를 명시한 게 프로젝트의 정체성을 지켜줬어요.

- **myeongni-seojae** — "오늘의 운세 87점"을 하지 않아요. 대신 대운
  타임라인 하나에 집중했고, 그래서 "대운수가 1년 어긋나면 안 된다"는
  비기능 요구사항(정확도)이 도출됐어요.
- **pulse-dashboard** — 게이트에서 자동 재시도를 하지 않아요. 주문까지
  재시도되면 중복 주문이 되니까요. "안 하기로 한 것"도 요구사항이에요.
- **rhythm-godot** — 낙하 노트가 없어요. "타일 각도가 곧 박자"라는 문제
  정의 한 문장이 자료구조(노트 타임라인 제거)까지 결정했어요.

결정과 근거를 남기는 양식은 [기술 선택 기록](../humans/decisions.md)을
참고하세요 — 결정보다 근거가 오래 가요.

## A — Architecture: 책임을 가르는 선 하나

토이에서 반복해서 나온 아키텍처 결정은 대부분 "선 하나를 어디에 긋는가"
였어요.

- **시뮬레이션 ↔ 렌더러** — 시뮬이 렌더러를 import 하지 않으면 게임
  전체를 헤드리스로 검증할 수 있어요. 게임 4개가 각자 같은 결론에
  도달했어요. ([headless-harness](headless-harness.md))
- **SSOT에서 파생** — roomcast는 평면도 모델 하나에서 2D 에디터와 3D
  워크스루를 파생시켜요. 계산이 일어나는 위치를 한 곳으로 모으는 결정이에요.
- **뷰 ↔ 편집이 같은 상수를 본다** — pig-ma는 Konva 렌더링과 Tiptap
  오버레이가 같은 상수를 import 해요. 두 컴포넌트가 같은 값을 각자 들고
  있으면 반드시 갈라져요.

## D — Data Model: 데이터가 어디 살고 어떻게 변하나

- **콘텐츠는 코드 안의 순수 데이터** — crypt-survivors·dungeon-craft는
  무기·적·진화가 전부 `content/` 데이터라서, 추가가 엔진 수정이 아니라
  데이터 편집으로 끝나요.
- **좌표계는 타입으로 분리** — osm-walker는 WGS84 · LocalXZ · Screen을
  다른 타입으로 두고 변환은 파일 하나에서만 해요. 셋 다 그냥 숫자 두
  개라서, 타입을 안 나누면 컴파일러가 못 잡거든요.
- **스키마의 생명주기까지 설계** — 세이브 데이터는 방어적 검증으로 옛
  버전이 크래시하지 않게 하고, 필드 추가 시 등록처(fresh + 마이그레이션 +
  테스트)를 커맨드로 묶어서 하나를 빠뜨리지 않게 해요.

## I — Interface: 경계의 계약을 명시해요

- **외부 데이터는 문 앞에서 막아요** — Overpass API 응답처럼 스키마가
  느슨한 입력은 파싱 단계에서 Zod로 검증하고, 통과한 것만 안쪽으로
  보내요. 같은 데이터가 다른 문(localStorage 복원 vs 파일 import)으로
  들어오면 같은 검사를 받아야 해요.
- **남의 API 앞에 게이트 하나** — pulse-dashboard의 모든 KIS 호출은
  `kisFetch` 하나를 통과해요. 경계가 한 곳이면 정책(직렬 큐, 적응형
  간격)도 한 곳에서 바꿔요.
- **라이브러리 경계는 소비자 관점으로** — pig-ma는 Konva·Tiptap을 peer
  dependency로 빼서 소비 앱과 인스턴스를 공유해요. 경계 설계는 "내보내는
  쪽"이 아니라 "받는 쪽"의 사정에서 시작해요.

## O — Optimizations: NFR에서 나온 것만, 재고 나서

RADIO의 O가 말하는 "추측성 최적화 금지"를 토이에서는
[measure-first](measure-first.md)로 실천해요.

- pig에서 5,000 노드 캔버스가 느려졌을 때, 짐작(localStorage persist)은
  7%였고 진짜 범인(zoom 구독 리렌더)은 35%+였어요. 짐작대로 고쳤다면
  하루를 태우고 아무것도 못 얻었을 거예요.
- 잰 숫자는 커밋 메시지에 남기고, 문서에만 두지 않고 가능하면 테스트로
  잠가요.

## V — Verification: 완료를 증명해요

토이 방법론에서 가장 두터운 단계예요. "통과했다"가 아니라 "지킨다"를
증명하는 쪽으로요.

- **게이트는 깨뜨려 보고 커밋해요** — 일부러 위반을 주입해 잡히는지,
  되돌리면 통과하는지 양방향으로 확인해요.
  ([verification-gate](verification-gate.md))
- **부채 위에는 베이스라인 게이트** — 기존 부채를 고정하고 늘어난 것만
  실패시켜요. 베이스라인은 내려가는 쪽으로만 움직여요.
- **헤드리스 하네스로 수치화** — "해보니 어렵네"가 아니라 "24개 시드
  중앙값 생존 7분 12초"로요. 하네스를 만들면 하네스의 동기화 검사도 같이
  만들어요. ([headless-harness](headless-harness.md))
- **정답이 밖에 있으면 그것과 대조해요** — 절기 계산은 KASI 공식 값과,
  포팅은 원본 JS와 골든 코퍼스 diff로요. "내 구현 둘이 서로 맞다"와
  "공식 기관과 맞다"는 다른 문장이니까요.

## 깊이는 작업 크기에 맞춰요

RADIO 전 단계를 매번 다 도는 건 아니에요. 게이트(C/V)는 항상 지키되,
가운데는 작업 크기에 맞춰 골라요.

| 작업 크기 | Gate (C/V) | RADIO 단계 |
|---|---|---|
| 버그 수정 / 1일 작업 | 항상 | R |
| 기능 추가 / 1주 작업 | 항상 | R, D, I |
| 시스템 설계 / 1달+ | 항상 | R, A, D, I, O |

토이 프로젝트 하나를 새로 시작하는 건 보통 "시스템 설계" 쪽이라 전 단계를
돌고, 기존 토이에 콘텐츠를 얹는 건 R(+D) 정도로 충분하더라고요.
