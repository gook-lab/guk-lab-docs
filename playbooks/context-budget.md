# 에이전트 착수 전 읽기량 — 슬라이싱과 룰 스코프

에이전트가 일을 시작하기 전에 읽는 문서가 늘어나면, 아무도 안 보는 사이에
**작업 하나가 시작도 하기 전에 2만 토큰**을 씁니다. 사람이 쓰는 시간이 아니라
매 작업마다, 에이전트마다 반복해서 붙는 비용이라 눈에 잘 안 띕니다.

`malt-index`(문서 허브 + FE 레포로 나뉜 비공개 토이)에서 기능 에이전트 열 개를
병렬로 돌리며 겪은 것입니다.

## 먼저 쟀습니다 — 25,694 토큰

지침이 시키는 대로 읽으면 얼마인지부터 셌습니다. 2026-08-25 기준, 글자 수를
2.2로 나눈 어림치입니다.

| 문서 | ~토큰 |
|---|---|
| 프로젝트 `CLAUDE.md` | 1,270 |
| 하네스 운영 규약 | 6,428 |
| 제품 정의 | 1,246 |
| **기능별 API 계약** | **6,955** |
| 화면 이동 | 1,573 |
| FE 규약 | 3,050 |
| FE 아키텍처 | 5,172 |
| 합계 | **25,694** |

그런데 F5 기능을 만드는 에이전트에게 필요한 계약은 **계약 문서의 F5 절 하나**
입니다. 나머지 아홉 개 기능의 API 표를 다 읽고 시작하고 있었습니다.

> 이 어림치(글자÷2.2)는 정확한 토큰 수가 아닙니다. **비교용**입니다. 절대값이
> 필요하면 실제 토크나이저로 재야 합니다. 여기서 필요한 것은 "무엇이 큰가"였고
> 그건 어림치로도 갈립니다. ([measure-first](measure-first.md))

## 자를 수 있는 문서와 없는 문서

계약 문서는 `## F5.` 처럼 **절 경계가 기계적으로 분명**했습니다. 그래서 슬라이싱
도구를 하나 만들었습니다 — 공통 규약 + 해당 기능 절 + 부록만 뽑습니다.

| | 글자 | ~토큰 |
|---|---|---|
| 계약 문서 통째 | 15,300 | 6,955 |
| 슬라이스 (F1~F10 평균) | 3,015 | 1,370 |
| 줄어든 양 | | **약 5,600 / 기능** |

기능 열 개면 약 56,000 토큰입니다.

**화면 이동 문서와 아키텍처 문서는 안 잘랐습니다.** 절과 기능 번호의 대응이
문서 어디에도 안 적혀 있어서, 대응표를 도구 안에 만들어야 했기 때문입니다.
그 표는 문서가 바뀌면 **조용히 낡습니다** — 링크가 죽는 것과 달리 아무도
알아채지 못합니다. 대신 절 목차와 줄 범위를 찍어 주고 필요한 절만
`sed -n '238,304p'` 로 읽게 했습니다.

> 자를지 말지의 기준은 **문서 안에 경계가 적혀 있는가**입니다. 도구가 경계를
> 추측해야 한다면 자르지 않는 편이 낫습니다.

## 잘라낸 것을 출력 끝에 적습니다

슬라이스 출력 끝에 **뺀 절의 목록**을 항상 붙입니다.

```
`HANDOFF.md` 에서 뺀 절: F1. 계정·가입, F2. 보틀 카탈로그·검색, …
다른 기능의 계약입니다. 필요하면 `brief.py <코드>` 로 따로 뽑습니다.
```

안 적으면 읽는 쪽이 **그게 전부인 줄 압니다.** 잘린 것을 모르는 요약은 요약이
아니라 오해입니다.

## 도구만 만들면 절감이 안 납니다

여기가 이 플레이북에서 제일 중요한 부분입니다.

도구를 만들어 놓고 재보니 **읽는 양이 그대로였습니다.** 태스크 본문의 공통
규약이 여전히 *"`BRIEF.md` · `HANDOFF.md` · `FLOWS.md` · `FRONTEND.md` 를 먼저
읽어라"* 라고 지시하고 있었기 때문입니다. FE 레포의 `CLAUDE.md` 는 더
얄궂었습니다 — 이미 *"`HANDOFF.md`(해당 F 절)"* 이라고 적혀 있었는데,
**뽑는 수단이 없어서** 결국 통째로 읽고 그 절을 찾고 있었습니다.

- 의도만 적힌 지침(*"해당 절만"*)은 수단이 없으면 지켜지지 않습니다
- 절감은 **지시문을 고친 뒤에** 납니다. 도구는 절반입니다
- 지시문이 여러 곳에 흩어져 있으면(태스크 본문 · 레포별 `CLAUDE.md`) 전부
  찾아 고쳐야 합니다. 한 곳만 고치면 절반만 절약됩니다

## 규칙 파일은 스코프를 겁니다

규칙을 `.claude/rules/` 에 쌓으면 세션마다 전부 실립니다. 파일 앞에 프론트매터로
**언제 필요한지**를 적으면 관련 파일을 만질 때만 불러옵니다.

```markdown
---
description: 문서 파일명·번호 발급·본문 구조
globs: ["docs/**", "status/**", "*.md"]
---
```

- `globs` 가 없는 규칙은 전역입니다. **전역으로 둘 것은 실제로 전역인 것만**
  남깁니다(동시작업·보안처럼 어디서든 걸리는 것)
- 규칙 하나가 200줄을 넘으면 스코프를 걸어도 비쌉니다. 그때는 규칙을 쪼개거나,
  본문을 도구로 옮길 수 있는지 봅니다

## 긴 문서에는 절 인덱스를 붙입니다

운영 규약이 476줄이 되자 에이전트가 통째로 읽었습니다. 앞에 *"하려는 것 → 절
번호"* 표를 붙여서 필요한 절로 바로 가게 했습니다.

| 하려는 것 | 절 |
|---|---|
| 태스크가 왜 아직 대기인가 | 2 |
| 동시에 몇 개까지 돌려도 되나 | 4 |
| 충돌이 났다 | 10 |

목차(`## 제목` 나열)와 다릅니다. 목차는 **문서가 무엇을 담는지**를 보여주고,
이 표는 **읽는 사람이 무엇을 하려는지**에서 출발합니다.

## 작업 크기에 맞춰 얹습니다

읽기량과 별개로, 작업마다 서브에이전트·워크플로·다라운드 검증을 습관적으로
얹으면 문서 한 건에도 몇 배가 듭니다. 티어를 정해 두는 편이 낫습니다.

| 작업 | 처리 |
|---|---|
| 문서·오타·설정·1~2 파일 수정, 조회 | 직접 합니다. 위임 없음 |
| 기능 구현 | 태스크 하나에 에이전트 하나 |
| 머지 · 계약 변경 · 배포 판단 | 검토를 붙입니다 |

- **게이트는 되돌리기 비용이 큰 지점**입니다. *"꼼꼼히 보고 싶다"* 는 게이트가
  아닙니다
- 결함이 0으로 수렴하면 거기서 끝냅니다. *"한 번 더"* 를 붙이지 않습니다
- 여러 에이전트를 띄우기 전에 **"에이전트 N개 · 예상 M분"** 을 먼저 알립니다.
  승인을 받으라는 게 아니라, *"그건 그냥 직접 해"* 라고 할 기회를 만드는 것입니다

## 요약

1. **재고 시작합니다.** 지침대로 읽으면 몇 토큰인지부터 셉니다
2. 절 경계가 **문서에 적혀 있는** 것만 자릅니다. 추측해야 하면 목차와 줄 범위만 줍니다
3. **잘라낸 것을 출력에 적습니다**
4. **지시문을 같이 고칩니다.** 도구만으로는 절감이 안 납니다
5. 규칙에 `globs` 를 겁니다. 전역은 진짜 전역인 것만
6. 긴 문서에는 *"하려는 것 → 절"* 표를 붙입니다
